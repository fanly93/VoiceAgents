## Plan Summary

Build Phase 0 assets for the VoiceAgents phone-channel MVP:

- Real-call evaluation corpus schema.
- Synthetic redacted sample evaluation data.
- Validation script and tests.
- MVP tool contracts.
- Handoff and failure rules.
- Repo-level docs that can be committed and shared.

## Scope Detection

- UI scope: no.
- DX scope: yes. The current deliverable is used by product, engineering, and annotation teams before implementation.
- Production phone system scope: no.

## CEO Review

Decision: keep scope narrow.

The approved product thesis is strong enough to proceed, but the riskiest assumption is not whether merchants want phone support. The risky part is whether real calls can be understood and safely routed with enough quality to preserve trust.

Real pilot recordings are not available yet, so the real-call evaluation portion is deferred. This does not block schema, contracts, validation tooling, or MVP planning.

Autoplan decision:

- Do not start with a full voice platform.
- Do not start with telephony integration.
- First prove the evaluation and contract baseline with synthetic redacted samples.
- Re-run Phase 0 with real call samples once recordings become available.

Deferred scope:

- Multi-language.
- Outbound calls.
- Merchant configuration UI.
- Automated return/refund handling.
- QA dashboards.

## Engineering Review

Key engineering risks:

| Risk | Impact | Decision |
|---|---|---|
| Real recordings may contain PII | Compliance and repo safety risk | Store only safe references; never commit audio or raw PII |
| Order ID recognition may be unreliable | Wrong answers damage trust | Require repeat-back confirmation and handoff |
| RAG text may be unsuitable for phone | Poor user experience | Track expected voice response summary separately |
| Tool contracts may drift from existing SaaS APIs | Integration rework | Keep Phase 0 contracts explicit and small |
| Handoff context may be incomplete | Human agent repeats questions | Require intent, order candidate, tools called, and reason |

Implementation decision:

- Use a small Python schema validator and pytest suite.
- Avoid external dependencies.
- Keep sample data synthetic and redacted.

## DX Review

Current developer journey:

1. Read `README.md`.
2. Review approved design and spec under `docs/`.
3. Add or update call evaluations under `data/call-evaluations/`.
4. Run `python3 scripts/validate_call_evaluations.py data/call-evaluations/sample.json`.
5. Run `python3 -m pytest`.

TTHW target: under 5 minutes for a new contributor to validate the sample corpus.

DX decisions:

- Keep commands short.
- Make validation failure messages point to `call_id` and field.
- Keep contracts in Markdown so product, support, and engineering can review them.

## Failure Modes Registry

| Failure Mode | Rescue |
|---|---|
| Dataset is not an array or `{ calls: [] }` | Validator exits nonzero with dataset error |
| Missing required annotation field | Validator reports `call_id`, field, and reason |
| Invalid intent/tool/handoff enum | Validator lists allowed values |
| Handoff call has no handoff reason | Validator rejects it |
| Non-handoff call has a handoff reason | Validator rejects it |
| Confidence is outside 0-1 | Validator rejects it |
